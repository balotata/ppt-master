# Narrative System

Use this file to build the story, outline, slide claims, and speaker notes.

## Claim Spine

Before designing substantial decks, define:

- Thesis: one sentence that states the deck's point of view.
- Audience: who must believe or do something.
- Arc: how the story moves, e.g. `pain -> mechanism -> consequence -> principle`, `myth -> reality -> system -> strategy`, `past -> friction -> breakthrough -> future`, or `case -> pattern -> model -> action`.
- Slide list: each slide has a claim, proof object, source, and omission note.

Bad title: `Revenue and margin trends`  
Good title: `Growth slowed, but the margin engine kept expanding.`

Bad title: `AI agent architecture`  
Good title: `The agent layer moves work from screens to delegated loops.`

## Slide Contract

Every non-appendix slide should answer one question:

- What should the audience believe after this slide?
- What proof makes that belief credible?
- What visual structure makes the proof readable?
- What can be omitted without weakening the claim?

If two ideas compete, split them. If a slide cannot support a claim, demote it to appendix or delete it.

## Page Types

Use these as building blocks, not rigid templates:

- Cover / thesis
- Agenda as argument
- Core tension
- Market or context frame
- Timeline
- Case frame
- Mechanism
- Loop diagram
- Data highlight
- Chart proof
- Comparison
- Matrix
- Product or system map
- Process
- Risk boundary
- Decision page
- Principles
- Roadmap
- Appendix/source page
- Closing thesis

## Copy Rules

- Write for a speaker's mouth, not a whitepaper.
- Use short, exact sentences.
- Delete filler: "由此可见", "总而言之", "在某种程度上", "赋能", "生态闭环" unless the deck defines them concretely.
- Avoid generic AI phrasing and consulting wallpaper.
- Bind abstract claims to specific behavior, data, tradeoffs, or examples.
- Bilingual decks should be meaning-matched, not word-for-word translated.
- Let philosophical tone come from rhythm and precision, not terminology.

## Speaker Notes

Use speaker notes when the deck is for live delivery, executive persuasion, teaching, or complex analysis.

Good notes:

- Explain the conflict in plain language.
- Add one example, analogy, or caveat not already on the slide.
- Keep a spoken rhythm.
- Do not simply read the slide.

## Outline Checkpoint

For heavy, long, research-backed, or image-heavy decks, provide a Markdown outline before building unless the user asked for immediate production. Include per slide:

- Page type
- Claim title
- Core proof object
- Visual direction
- Speaker note intent
- Source requirement or uncertainty
